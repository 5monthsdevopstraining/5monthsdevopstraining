# Private EKS Deployment: Complete Build Guide

Task: create a **private EKS cluster** and deploy the sample .NET app (`app/`) on it, reachable from the internet.

This stack is **standalone**. It creates its own VPC, cluster, registry and bucket, and does not need
last week's `terraform/` stack, Jenkins or RDS. Everything lives in the `eks/` folder. This guide lists
**every file** with its full content and explains why it exists. Then it gives the commands to build,
deploy, test and clean up. Follow it from top to bottom.

---

## 1. What we are building

```
                     Internet user              Your laptop               GitHub (git push)
                          | HTTP :80            | SSH :22, Jenkins :8080   | webhook :8080
+-------------------------|------------ VPC ----|--------------------------|----------------+
|  Public subnets (2 AZ)  v                     v                          v                |
|                   [ Public ALB ]      [ Deployer EC2 + Jenkins (Elastic IP) ]   [ NAT ]    |
|                         | to pod IPs           | kubectl/helm :443                 ^        |
|  Private subnets (2 AZ) v                      v                                   |        |
|                   [ App pods x2 ] <---- [ EKS API (private endpoint) ]             |        |
|                   on [ 2 worker nodes ] ------------------------------------------+        |
|                         | :5432                                                            |
|                   [ RDS PostgreSQL ]                                                       |
+--------------------------------------------------------------------------------------------+
   git push -> Jenkins: docker build -> push to [ ECR ] -> helm + kubectl apply -> nodes pull the image
   App pods upload files to [ S3 ] with EKS Pod Identity (no AWS keys) and read RDS settings from a K8s Secret.
```

| Piece | What it is | Why |
| --- | --- | --- |
| VPC | 2 public + 2 private subnets in 2 AZs, 1 NAT gateway | Its own network. Nodes and pods have private IPs only. |
| EKS cluster | Kubernetes 1.37, **private API endpoint only** | The task: a private cluster. Nothing outside the VPC can call the Kubernetes API. |
| Node group | 2 x c7i-flex.large in the private subnets | Run the app pods. A Free plan AWS account can only launch Free Tier types; this is the one big enough (t3.micro fits only 4 pods per node). |
| Deployer EC2 | c7i-flex.large in a **public** subnet (Elastic IP) with docker, kubectl, helm and **Jenkins** | The API is private, so kubectl has to run inside the VPC. It builds the image and deploys it. You log in with **SSH** (key pair generated by Terraform); SSH and the Jenkins UI are open only to your IP. |
| Jenkins | Runs on the deployer, configured by Terraform | Deploys every `git push` to your branch (GitHub webhook, or polling every 2 minutes). |
| ECR | Private image registry | The deployer pushes the image here; nodes pull it. |
| S3 bucket | `uploads/` folder | Lets the app's upload API work. |
| RDS PostgreSQL | db.t4g.micro in the private subnets, password in Secrets Manager | Lets the app's database API work. Only the nodes/pods can reach it. |
| AWS Load Balancer Controller | Runs inside the cluster | Turns the Kubernetes Ingress into a public ALB. |
| Public ALB | Internet-facing, in public subnets | The only way in for users. Sends traffic straight to pod IPs. |
| Pod Identity | IAM roles for pods | App pods get S3 access and the LB controller gets ELB access, without keys. |

**Request flow:** user -> ALB (public subnet) -> pod IP (private subnet) -> S3 / RDS.

**First deploy (`terraform apply`):** create the infrastructure -> SSH to the deployer -> write the settings
and start Jenkins (`jenkins.tf`) -> upload `app/` + manifests and run `deploy-app.sh` (`deploy.tf`).

**Every later deploy (`git push`):** GitHub webhook -> Jenkins job `eks-sample-app` -> `eks/Jenkinsfile` ->
`deploy-app.sh` -> docker build + push to ECR -> helm + kubectl apply over the private endpoint -> pods roll out.

**Where you run the commands:** your laptop. It only needs Terraform, the AWS CLI and an SSH client. Docker and
kubectl run on the deployer EC2.

## 2. Prerequisites (on your laptop)

| Item | Check | Detail |
| --- | --- | --- |
| Terraform 1.10+ | `terraform version` | |
| AWS CLI v2 | `aws sts get-caller-identity --profile saranya` | Profile `saranya` |
| ssh | `ssh -V` | Terraform and the scripts log in to the deployer with it |
| git push access | `git push` works | Jenkins deploys what you push to your branch (`github_branch` in tfvars) |
| `GODEBUG=tlsmlkem=1` | `echo $GODEBUG` | See *Network fix* below |
| IAM permissions | | Create VPC/EKS/IAM/EC2/ECR/S3 resources and EC2 key pairs (an admin user is fine) |

kubectl, helm and docker are **not** needed on the laptop. They run on the deployer EC2.

**Network fix (needed on some networks, such as Jio):** Terraform's AWS provider is built with the ML-KEM
TLS key exchange switched off (`DefaultGODEBUG=tlsmlkem=0`). On networks that stall TLS handshakes without
ML-KEM, `terraform plan` hangs on `STS: GetCallerIdentity`, even though the AWS CLI and the browser work.
Turn ML-KEM back on for every terminal:

```bash
echo 'export GODEBUG=tlsmlkem=1' >> ~/.bashrc
source ~/.bashrc
```

`eks/scripts/lib.sh` sets the same variable for the scripts.

#### `eks/terraform/provider.tf`

**Why:** Pins the AWS provider, picks the AWS profile, and defines the names every other file uses.

Create it: `code eks/terraform/provider.tf` (or any editor), then paste:

```hcl
# Standalone Terraform project for the private EKS cluster.
# Creates everything it needs (VPC, EKS, ECR, S3, RDS, deployer EC2 with Jenkins) and deploys the app
# over SSH (deploy.tf) - nothing from ../../terraform is used.
# Runs from your laptop (aws_profile = "" uses the default AWS credentials instead of a profile).

terraform {
  required_version = ">= 1.10.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
    tls = { # SSH key pair for the deployer EC2
      source  = "hashicorp/tls"
      version = "~> 4.0"
    }
    local = { # writes the private key to deployer-key.pem
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
    http = { # looks up your public IP and GitHub's webhook IPs
      source  = "hashicorp/http"
      version = "~> 3.4"
    }
    random = { # Jenkins admin password
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
  }
}

provider "aws" {
  region  = var.aws_region
  profile = var.aws_profile == "" ? null : var.aws_profile # "" = default credentials
  default_tags {
    tags = local.common_tags
  }
}

data "aws_caller_identity" "current" {}

data "aws_availability_zones" "available" {
  state = "available"
}

locals {
  name_prefix  = "${var.project}-${var.environment}-${var.aws_region}"
  cluster_name = "${local.name_prefix}-eks-app"
  azs          = slice(data.aws_availability_zones.available.names, 0, 2)

  # Must match eks/k8s/*.yaml
  k8s_namespace       = "sample-app"
  k8s_service_account = "sample-app"

  # Must match LBC_SA in eks/scripts/deploy-app.sh
  lbc_namespace       = "kube-system"
  lbc_service_account = "aws-load-balancer-controller"

  # Folder in the S3 bucket (s3.tf) for files uploaded through the app
  upload_prefix = "uploads"

  common_tags = {
    Project     = var.project
    Environment = var.environment
    Owner       = var.owner
    CreatedBy   = var.created_by
    ManagedBy   = "Terraform"
    Stack       = "eks"
  }
}
```

**Key points:**

- `name_prefix` = `sample-dev-ap-south-1`, so the cluster is `sample-dev-ap-south-1-eks-app`.
- `profile = var.aws_profile == "" ? null : ...`: works with a named profile or with default credentials.
- `azs` takes the first 2 availability zones of the region, so the setup has 2 subnets of each type.
- `k8s_namespace` / `k8s_service_account` must match the YAML in `eks/k8s/`. Pod Identity links IAM roles to this exact namespace + service account.
- `upload_prefix` is the S3 folder the app writes to.
- Besides `aws`, it uses `tls` (generates the SSH key), `local` (writes `deployer-key.pem`) and `http` (looks up your public IP).
- `default_tags` puts Project/Owner/... and `Stack = eks` on every resource.

- `github_branch`: Jenkins deploys pushes to this branch.

#### `eks/terraform/vpc.tf`

**Why:** The network: public subnets for the ALB and NAT, private subnets for everything else.

Create it: `code eks/terraform/vpc.tf` (or any editor), then paste:

```hcl
# VPC for the private EKS cluster:
#   public subnets  (2 AZs) -> internet-facing ALB + NAT gateway + deployer EC2 (SSH jump box)
#   private subnets (2 AZs) -> EKS API endpoint ENIs, worker nodes, pods
# Nodes have no public IP; they reach the internet (ECR, EKS) through the NAT.

resource "aws_vpc" "this" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true # required for the private EKS endpoint

  tags = { Name = "${local.name_prefix}-vpc-eks" }
}

resource "aws_internet_gateway" "this" {
  vpc_id = aws_vpc.this.id
  tags   = { Name = "${local.name_prefix}-igw-eks" }
}

resource "aws_subnet" "public" {
  count = 2

  vpc_id                  = aws_vpc.this.id
  availability_zone       = local.azs[count.index]
  cidr_block              = cidrsubnet(var.vpc_cidr, 4, count.index) # 10.20.0.0/20, 10.20.16.0/20
  map_public_ip_on_launch = true

  tags = {
    Name                     = "${local.name_prefix}-subnet-eks-public${count.index + 1}"
    Tier                     = "public"
    "kubernetes.io/role/elb" = "1" # AWS Load Balancer Controller puts internet-facing ALBs here
  }
}

resource "aws_subnet" "private" {
  count = 2

  vpc_id            = aws_vpc.this.id
  availability_zone = local.azs[count.index]
  cidr_block        = cidrsubnet(var.vpc_cidr, 4, count.index + 8) # 10.20.128.0/20, 10.20.144.0/20

  tags = {
    Name                              = "${local.name_prefix}-subnet-eks-private${count.index + 1}"
    Tier                              = "private"
    "kubernetes.io/role/internal-elb" = "1" # internal ALBs (not used by the sample app)
  }
}

########## Routing ##########

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.this.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.this.id
  }

  tags = { Name = "${local.name_prefix}-rt-eks-public" }
}

resource "aws_route_table_association" "public" {
  count = 2

  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
}

# One NAT gateway (cheaper for training; use one per AZ in production)
resource "aws_eip" "nat" {
  domain = "vpc"
  tags   = { Name = "${local.name_prefix}-eip-eks-nat" }
}

resource "aws_nat_gateway" "this" {
  allocation_id = aws_eip.nat.id
  subnet_id     = aws_subnet.public[0].id
  tags          = { Name = "${local.name_prefix}-nat-eks" }

  depends_on = [aws_internet_gateway.this]
}

resource "aws_route_table" "private" {
  vpc_id = aws_vpc.this.id

  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.this.id
  }

  tags = { Name = "${local.name_prefix}-rt-eks-private" }
}

resource "aws_route_table_association" "private" {
  count = 2

  subnet_id      = aws_subnet.private[count.index].id
  route_table_id = aws_route_table.private.id
}
```

**Key points:**

- `enable_dns_hostnames` / `enable_dns_support` must be on. Otherwise the private EKS endpoint name does not resolve inside the VPC.
- `cidrsubnet(var.vpc_cidr, 4, n)` cuts /20 subnets: public 10.20.0.0/20 and 10.20.16.0/20, private 10.20.128.0/20 and 10.20.144.0/20. That is about 4,000 IPs each, plenty for pod IPs.
- **`kubernetes.io/role/elb = 1` on the public subnets:** the LB controller only places internet-facing ALBs in subnets with this tag.
- `kubernetes.io/role/internal-elb = 1` on the private subnets is for internal load balancers (standard, unused here).
- Private subnets route `0.0.0.0/0` to the NAT gateway. Nodes need it to pull images, join the cluster and reach S3 and ECR. One NAT keeps the cost down; production uses one per AZ.

#### `eks/terraform/cluster.tf`

**Why:** The EKS cluster, its add-ons, the worker nodes, the Pod Identity links and who may use kubectl.

Create it: `code eks/terraform/cluster.tf` (or any editor), then paste:

```hcl
# Private EKS cluster: the Kubernetes API has NO public endpoint (only reachable inside the VPC),
# and the worker nodes run in the private subnets (outbound via the NAT gateway in vpc.tf).

resource "aws_eks_cluster" "this" {
  name     = local.cluster_name
  version  = var.kubernetes_version
  role_arn = aws_iam_role.cluster.arn

  access_config {
    # kubectl access is granted with EKS access entries (bottom of this file), no aws-auth ConfigMap
    authentication_mode                         = "API"
    bootstrap_cluster_creator_admin_permissions = true
  }

  vpc_config {
    subnet_ids              = aws_subnet.private[*].id
    endpoint_private_access = true
    endpoint_public_access  = false # private cluster
  }

  depends_on = [
    aws_iam_role_policy_attachment.cluster,
    aws_route_table_association.private,
  ]
}

# EKS creates a "cluster security group" used by the control plane, the managed nodes and the pods.
# Allow the deployer EC2 to reach the private API endpoint.
resource "aws_vpc_security_group_ingress_rule" "api_from_deployer" {
  security_group_id            = aws_eks_cluster.this.vpc_config[0].cluster_security_group_id
  description                  = "Kubernetes API from the EKS deployer EC2"
  ip_protocol                  = "tcp"
  from_port                    = 443
  to_port                      = 443
  referenced_security_group_id = aws_security_group.deployer.id
}

########## Add-ons ##########

# Needed before nodes join: pod networking, kube-proxy and the Pod Identity agent
resource "aws_eks_addon" "core" {
  for_each = toset(["vpc-cni", "kube-proxy", "eks-pod-identity-agent"])

  cluster_name                = aws_eks_cluster.this.name
  addon_name                  = each.key
  resolve_conflicts_on_create = "OVERWRITE"
  resolve_conflicts_on_update = "OVERWRITE"
}

# CoreDNS runs as pods, so it needs nodes first
resource "aws_eks_addon" "coredns" {
  cluster_name                = aws_eks_cluster.this.name
  addon_name                  = "coredns"
  resolve_conflicts_on_create = "OVERWRITE"
  resolve_conflicts_on_update = "OVERWRITE"

  depends_on = [aws_eks_node_group.this]
}

resource "aws_eks_node_group" "this" {

  node_group_name = "${local.cluster_name}-ng-default"
  node_role_arn   = aws_iam_role.node.arn
  subnet_ids      = aws_subnet.private[*].id

  ami_type       = "AL2023_x86_64_STANDARD"
  capacity_type  = "ON_DEMAND"
  instance_types = [var.node_instance_type]

  scaling_config {
    desired_size = var.node_desired_size
    min_size     = var.node_min_size

    max_unavailable = 1
  }

    ignore_changes = [scaling_config[0].desired_size] # allow manual scaling
  }

  depends_on = [
    aws_iam_role_policy_attachment.node,
    aws_eks_addon.core,
  ]
}
```

**Key points:**

- **`endpoint_public_access = false` + `endpoint_private_access = true` is what makes the cluster private.** The API gets a DNS name that only resolves inside the VPC.
- `authentication_mode = "API"`: kubectl permissions come from EKS access entries (bottom of the file), not the old `aws-auth` ConfigMap.
- `bootstrap_cluster_creator_admin_permissions = true`: the IAM user who runs `terraform apply` is also a cluster admin.
- `api_from_deployer`: EKS creates a *cluster security group* that the control plane, nodes and pods use. This rule opens port 443 on it only for the deployer.
- Add-ons: `vpc-cni` (pod networking), `kube-proxy` (Service routing) and `eks-pod-identity-agent` (IAM for pods) are installed before nodes join. `coredns` (DNS) runs as pods, so it waits for the node group.
- Node group: managed by AWS (patching, draining). `ignore_changes` on `desired_size` lets you scale by hand without Terraform undoing it.
- `aws_eks_pod_identity_association` means "pods using service account X in namespace Y get IAM role Z". There is one for the app and one for the Load Balancer Controller.
- `aws_eks_access_entry` + `AmazonEKSClusterAdminPolicy` let the deployer EC2's role run any kubectl or helm command.

- **SSH key:** `tls_private_key` creates an ED25519 key, `aws_key_pair` registers the public half, and `local_sensitive_file` writes the private half to `eks/terraform/deployer-key.pem` (mode 0600, gitignored). The private key is also in the Terraform state, so keep the state private.
- **SSH access:** the instance is in a public subnet with a public IP. Port 22 and Jenkins (8080) are open only to `admin_cidrs`; when that is empty (the default), `data.http.my_ip` looks up your current public IP. If your IP changes, run `terraform apply` again to update the rules. Port 8080 is also open to GitHub's webhook ranges (`data.http.github_meta`, from `api.github.com/meta`).
- **Elastic IP:** the Jenkins URL, the webhook URL and the SSH address stay the same when the instance is stopped and started.
- The security group uses `create_before_destroy`, because the EKS API rule in `cluster.tf` points at it: the new group is created first, and the old one is deleted only when nothing references it.
- Log in: `./eks/scripts/ssh.sh`, or the command from `terraform output ssh_command`.
- `http_tokens = "required"` enforces IMDSv2. The disk is encrypted.
- `ignore_changes = [ami]` stops the instance being replaced every time AWS publishes a new AMI.
- 30 GB disk for the docker build cache of the .NET SDK image.
- `depends_on` the public route: user data downloads docker, kubectl and helm through the internet gateway.

#### `eks/terraform/scripts/deployer.sh`

**Why:** User data for the deployer EC2: installs docker, kubectl, helm and jq on first boot.

Create it: `code eks/terraform/scripts/deployer.sh` (or any editor), then paste:

```bash
#!/bin/bash
# User data for the EKS deployer EC2 (Amazon Linux 2023: AWS CLI v2 is preinstalled).
# Installs docker, kubectl, helm, jq, git and Jenkins (with its plugins).
# Jenkins is only enabled here, not started: eks/terraform/jenkins.tf writes its config
# (admin user, pipeline job) over SSH and then starts it.
# eks/terraform/jenkins.tf and deploy.tf wait (over SSH) for /var/lib/eks-deployer-ready.
set -euxo pipefail
exec > >(tee /var/log/user-data.log) 2>&1

KUBECTL_VERSION=v1.37.1 # keep within one minor version of the cluster (kubernetes_version)
HELM_VERSION=v3.21.1
PLUGIN_MANAGER_VERSION=2.16.0 # github.com/jenkinsci/plugin-installation-manager-tool

curl -fsSL -o /etc/yum.repos.d/jenkins.repo https://pkg.jenkins.io/rpm-stable/jenkins.repo
until dnf install -y docker jq tar gzip git fontconfig java-21-amazon-corretto-headless jenkins; do
  echo "dnf failed, retrying in 10s"; sleep 10
done
systemctl enable --now docker
usermod -aG docker ec2-user # "docker" without sudo after you SSH in
usermod -aG docker jenkins  # Jenkins builds the image

# 2 GB swap: headroom for the .NET build next to Jenkins
if [ ! -f /swapfile ]; then
  dd if=/dev/zero of=/swapfile bs=1M count=2048 status=none
  chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
  echo "/swapfile swap swap defaults 0 0" >> /etc/fstab
fi

until curl -fsSL -o /usr/local/bin/kubectl "https://dl.k8s.io/release/${KUBECTL_VERSION}/bin/linux/amd64/kubectl"; do
  echo "kubectl download failed, retrying in 10s"; sleep 10
done
chmod +x /usr/local/bin/kubectl

until curl -fsSL "https://get.helm.sh/helm-${HELM_VERSION}-linux-amd64.tar.gz" -o /tmp/helm.tgz; do
  echo "helm download failed, retrying in 10s"; sleep 10
done
tar xzf /tmp/helm.tgz -C /tmp && mv /tmp/linux-amd64/helm /usr/local/bin/helm && rm -rf /tmp/helm.tgz /tmp/linux-amd64

# deploy-app.sh is run by Terraform (as root) and by Jenkins: this lock makes them take turns
install -m 0666 /dev/null /var/lib/eks-deploy.lock

########## Jenkins ##########

until curl -fsSL -o /opt/jenkins-plugin-manager.jar \
  "https://github.com/jenkinsci/plugin-installation-manager-tool/releases/download/${PLUGIN_MANAGER_VERSION}/jenkins-plugin-manager-${PLUGIN_MANAGER_VERSION}.jar"; do
  echo "plugin manager download failed, retrying in 10s"; sleep 10
done

# configuration-as-code: config from casc.yaml | job-dsl: creates the pipeline job
# workflow-aggregator: pipelines | git + github: checkout and the push webhook
until java -jar /opt/jenkins-plugin-manager.jar \
  --war /usr/share/java/jenkins.war \
  --plugin-download-directory /var/lib/jenkins/plugins \
  --plugins configuration-as-code job-dsl workflow-aggregator git github timestamper ws-cleanup; do
  echo "plugin download failed, retrying in 10s"; sleep 10
done
chown -R jenkins:jenkins /var/lib/jenkins

# No setup wizard; read the config written by Terraform; keep the heap small next to the docker build
mkdir -p /etc/systemd/system/jenkins.service.d
cat > /etc/systemd/system/jenkins.service.d/override.conf <<'EOF'
[Service]
Environment="JAVA_OPTS=-Djava.awt.headless=true -Djenkins.install.runSetupWizard=false -Xmx1g"
Environment="CASC_JENKINS_CONFIG=/var/lib/jenkins/casc.yaml"
EOF
systemctl daemon-reload
systemctl enable jenkins

touch /var/lib/eks-deployer-ready
echo "EKS deployer ready"
```

**Key points:**

- Jenkins comes from the official RPM repo with Java 21 (Corretto). Its plugins are downloaded with the Jenkins plugin manager. It is only enabled here; `jenkins.tf` starts it after writing its config, so it never runs unsecured.
- `jenkins` and `ec2-user` join the `docker` group.
- `/var/lib/eks-deploy.lock` lets `deploy-app.sh` runs from Terraform and Jenkins take turns.
- 2 GB swap: headroom for the .NET SDK build next to Jenkins.
- `until ...; do sleep 10; done` loops retry while the NAT route or the package mirrors are not ready yet.
- `ec2-user` joins the `docker` group, so `docker` works without `sudo` after you SSH in.
- `/var/lib/eks-deployer-ready` is written last. `deploy.tf` waits for it over SSH, so the deploy never runs on a half-installed box.
- Logs: `sudo cat /var/log/user-data.log` after `./eks/scripts/ssh.sh`.

#### `eks/terraform/deploy.tf`

Create it: `code eks/terraform/deploy.tf` (or any editor), then paste:

```hcl
# First deploy of the app as part of "terraform apply", over SSH to the deployer EC2
# (after that, Jenkins deploys every git push - see jenkins.tf and eks/Jenkinsfile):
#   1. upload app/, eks/k8s/ and eks/scripts/deploy-app.sh from your laptop (file provisioner = scp),
#      in the same layout as the git repo, so Jenkins runs the very same script from its checkout
#   2. run deploy-app.sh: docker build + push to ECR, AWS Load Balancer Controller, ConfigMap,
#      RDS Secret, Deployment, Service, Ingress (ALB), wait until the app answers
# It runs again when your local app source, the manifests, the script, the settings or the EC2 change.

locals {
  app_dir     = "${path.module}/../../app"
  k8s_dir     = "${path.module}/../k8s"
  deploy_file = "${path.module}/../scripts/deploy-app.sh"
  remote_dir  = "/home/ec2-user/eks-deploy" # = repo root layout: app/, eks/k8s/, eks/scripts/

  # Hash of everything that ends up in the image or the cluster (bin/ and obj/ are build output)
  app_files = sort([for f in fileset(local.app_dir, "**") : f
  if !can(regex("^(bin|obj|\\.vs|build-check)/", f))])
  deploy_hash = sha1(join(",", concat(
    [for f in local.app_files : filesha1("${local.app_dir}/${f}")],
    [for f in sort(fileset(local.k8s_dir, "*.yaml")) : filesha1("${local.k8s_dir}/${f}")],
    [filesha1(local.deploy_file)],
  )))
  image_tag = "tf-${substr(local.deploy_hash, 0, 12)}" # new source -> new tag -> pods roll

  ssh_connection = {
    type        = "ssh"
    host        = aws_eip.deployer.public_ip
    user        = "ec2-user"
    private_key = tls_private_key.deployer.private_key_openssh
  }
}

```

**Key points:**

- **Provisioners over SSH:** the `connection` block uses the deployer's public IP, `ec2-user` and the generated key. `file` provisioners copy `app/`, `eks/k8s/` and `deploy-app.sh` (like `scp`); `remote-exec` runs commands. Their output streams into the `terraform apply` log.
- **When it redeploys:** `triggers_replace` holds a hash of every file in `app/` (minus `bin/`, `obj/`), the manifests and `deploy-app.sh`, the instance ID and the deploy settings (not Jenkins-only changes). Change any of them and the next `terraform apply` builds and deploys again. No change = nothing to do.
- **Image tag** = the first 12 characters of that hash, so new code gets a new tag and the pods roll.
- `depends_on` makes sure the nodes, CoreDNS, the deployer's access entry, Pod Identity and the API security group rule exist before the deploy starts.
- **`ingress_cleanup`** has a destroy-time provisioner: on `terraform destroy` it deletes the Ingress (so the LB controller removes the ALB and its security groups, which Terraform doesn't know about and which would block deleting the VPC), then uninstalls the controller. It is a separate resource so that a redeploy doesn't delete the ALB. `on_failure = continue`: if the cluster is already broken, destroy still goes on.
- Force a redeploy without code changes: `terraform apply -replace=terraform_data.deploy`.

#### `eks/Jenkinsfile`

**Why:** The pipeline the Jenkins job runs on every push.

Create it: `code eks/Jenkinsfile` (or any editor), then paste:

```groovy
// Pipeline for the private EKS deployment. Jenkins runs on the deployer EC2 inside the EKS VPC
// (eks/terraform/jenkins.tf creates the job "eks-sample-app" that points here).
// Every push to the branch (GitHub webhook, or polling every 2 minutes) builds app/ with docker,
// pushes it to ECR and rolls it out to the cluster with eks/scripts/deploy-app.sh.
// Cluster, ECR, S3 and RDS settings come from /etc/eks-deploy.env (written by Terraform).

pipeline {
  agent any

  triggers {
    githubPush()            // instant, when the GitHub webhook is configured
    pollSCM('H/2 * * * *')  // fallback: check the branch for new commits every ~2 minutes
  }

  options {
    disableConcurrentBuilds()
    timeout(time: 30, unit: 'MINUTES')
    timestamps()
    buildDiscarder(logRotator(numToKeepStr: '20'))
  }

  stages {
    stage('Build and deploy to EKS') {
      steps {
        // Image tag = build number + commit, so every build is traceable in ECR and in the pods
        sh 'bash eks/scripts/deploy-app.sh "${BUILD_NUMBER}-$(git rev-parse --short HEAD)"'
      }
    }
  }

  post {
    always {
      cleanWs() // the workspace is a full copy of the repo; free the disk for docker
    }
  }
}
```

**Key points:**

- Jenkins runs **on** the deployer EC2, so the pipeline calls `deploy-app.sh` directly: no SSH, no stored keys. docker, kubectl, helm and the AWS CLI use the EC2's IAM role.
- Image tag `<build number>-<short commit>`: you can see in ECR and in `kubectl describe pod` exactly which commit is running.
- `disableConcurrentBuilds()` + the lock in `deploy-app.sh`: only one deploy runs at a time, even when `terraform apply` deploys at the same moment.
- This is separate from the repo-root `Jenkinsfile`, which belongs to the older EC2 stack in `terraform/`.

#### `eks/k8s/02-deployment.yaml`

**Why:** Runs 2 copies of the app container and keeps them healthy.

Create it: `code eks/k8s/02-deployment.yaml` (or any editor), then paste:

```yaml
# IMAGE_PLACEHOLDER, the "sample-app-config" ConfigMap (region, S3 bucket, folder) and the
# "sample-app-db" Secret (RDS connection string) are filled in at deploy time by eks/scripts/deploy-app.sh.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-app
  namespace: sample-app
  labels:
    app: sample-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: sample-app
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      serviceAccountName: sample-app
      # Spread the replicas over both AZs when possible
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels:
              app: sample-app
      securityContext:
        runAsNonRoot: true
        runAsUser: 1654 # "app" user built into the mcr.microsoft.com/dotnet/aspnet image
      containers:
        - name: app
          image: IMAGE_PLACEHOLDER
          ports:
            - name: http
              containerPort: 8080
          envFrom:
            - configMapRef:
                name: sample-app-config
            - secretRef:
                name: sample-app-db
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              memory: 512Mi
          readinessProbe:
            httpGet:
              path: /swagger/index.html
              port: http
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /swagger/index.html
              port: http
            initialDelaySeconds: 20
            periodSeconds: 20
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
```

**Key points:**

- `image: IMAGE_PLACEHOLDER` is replaced by `deploy-app.sh` with `<ecr-url>:<tag>` on every deploy.
- `maxUnavailable: 0`, `maxSurge: 1`: a new pod starts and becomes ready before an old one stops, so there is no downtime.
- `topologySpreadConstraints`: tries to put one pod in each AZ.
- `runAsUser: 1654` is the non-root `app` user built into Microsoft's aspnet image. `allowPrivilegeEscalation: false` and dropping all capabilities harden the container.
- `envFrom: configMapRef sample-app-config`: env vars `AWS__Region`, `S3__BucketName` and `S3__KeyPrefix`. ASP.NET reads `__` as `:`, so they override `appsettings.json`.
- Probes use `/swagger/index.html`, which the app already serves. Readiness decides when a pod gets traffic; liveness restarts a stuck pod.
- Requests (100m CPU, 128Mi) help the scheduler place pods. The 512Mi memory limit stops a leak from taking down the node.

#### `eks/k8s/04-ingress.yaml`

**Why:** Asks the AWS Load Balancer Controller for a public ALB in front of the Service.

Create it: `code eks/k8s/04-ingress.yaml` (or any editor), then paste:

```yaml
# The AWS Load Balancer Controller turns this into an internet-facing ALB in the PUBLIC subnets
# that forwards straight to the pod IPs in the PRIVATE subnets (target-type: ip).
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: sample-app
  namespace: sample-app
  annotations:
    alb.ingress.kubernetes.io/load-balancer-name: sampleapp-eks # name of the ALB in the EC2 console
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}]'
    alb.ingress.kubernetes.io/healthcheck-path: /swagger/index.html
spec:
  ingressClassName: alb
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: sample-app
                port:
                  name: http
```

**Key points:**

- `ingressClassName: alb` hands this Ingress to the AWS Load Balancer Controller.
- `scheme: internet-facing`: the ALB goes in the public subnets, the ones tagged `kubernetes.io/role/elb`.
- `target-type: ip`: the ALB sends traffic directly to pod IPs in the private subnets. The controller opens the security group rules it needs by itself.
- `load-balancer-name: sampleapp-eks`: a fixed name, so it is easy to find in the EC2 console.
- `healthcheck-path`: the ALB only sends traffic to pods that answer 200 on this path.

#### `eks/scripts/lib.sh`

**Why:** Shared helpers that the other laptop scripts `source`.

Create it: `code eks/scripts/lib.sh` (or any editor), then paste:

```bash
#!/bin/bash
# Shared helpers for ssh.sh / kubectl.sh (run on your laptop).
# Reads the Terraform outputs of eks/terraform and connects to the deployer EC2 over SSH.

TF_DIR=$(cd "$(dirname "${BASH_SOURCE[0]}")/../terraform" && pwd)

# The AWS provider is built with ML-KEM TLS key exchange switched off (DefaultGODEBUG=tlsmlkem=0).
# Some networks (seen on Jio) stall TLS handshakes without it, so terraform hangs on STS:GetCallerIdentity.
export GODEBUG=${GODEBUG:-tlsmlkem=1}

tf_out() {
  terraform -chdir="$TF_DIR" output -raw "$1"
}

HOST=$(tf_out deployer_public_ip)
KEY=$(tf_out deployer_key_file)

# The host key changes every time the instance is replaced, so don't pin it in ~/.ssh/known_hosts
SSH_OPTS=(-i "$KEY" -o StrictHostKeyChecking=accept-new -o UserKnownHostsFile=/dev/null -o LogLevel=ERROR)

# remote_ssh [ssh args...] - ssh to ec2-user on the deployer
remote_ssh() {
  ssh "${SSH_OPTS[@]}" "ec2-user@$HOST" "$@"
}
```

**Key points:**

- `tf_out` reads Terraform outputs, so the IP and key file always match what was created.
- `remote_ssh` runs `ssh -i deployer-key.pem ec2-user@<ip> ...`. The host key isn't saved to `~/.ssh/known_hosts`, because it changes whenever the instance is replaced.

#### `eks/scripts/deploy-app.sh`

**Why:** Runs on the deployer EC2 inside the VPC: builds and pushes the image, installs the LB controller and applies the manifests.

Create it: `code eks/scripts/deploy-app.sh` (or any editor), then paste:

```bash
#!/bin/bash
# Builds the app and deploys it to the private EKS cluster. Runs ON the deployer EC2, started by:
#   - Jenkins on every git push (eks/Jenkinsfile), as user jenkins, from its checkout of the repo
#   - "terraform apply" (eks/terraform/deploy.tf) over SSH, as root, from the files copied from your laptop
# Steps:
#   0. docker build app/ and push it to ECR (with the EC2's IAM role)
#   1. kubeconfig for the private cluster
#   2. install/upgrade the AWS Load Balancer Controller (Helm)
#   3. app ConfigMap (region, S3 bucket, folder) + Secret with the RDS connection string
#   4. kubectl apply eks/k8s/ with the new image, wait for the rollout and the ALB address
#   5. wait until the app answers through the ALB
# Usage: deploy-app.sh <image_tag>
# Settings (cluster, ECR, S3, RDS) come from /etc/eks-deploy.env, written by eks/terraform/jenkins.tf.
# Expected layout = the git repo: <root>/app/Dockerfile, <root>/eks/k8s/*.yaml, <root>/eks/scripts/deploy-app.sh
set -euo pipefail
export PATH=/usr/local/bin:$PATH # sudo's secure_path doesn't include it (kubectl, helm)
[ "$(id -u)" = 0 ] && export HOME=/root # kubectl/helm keep their config there when run with sudo

TAG=${1:?usage: deploy-app.sh <image_tag>}

# shellcheck disable=SC1091
source /etc/eks-deploy.env # AWS_REGION CLUSTER VPC_ID BUCKET UPLOAD_PREFIX ECR_REPO RDS_*
REGION=$AWS_REGION
IMAGE="$ECR_REPO:$TAG"

REPO_ROOT=$(cd "$(dirname "$0")/../.." && pwd)
APP_DIR=$REPO_ROOT/app
K8S_DIR=$REPO_ROOT/eks/k8s
NAMESPACE=sample-app                 # must match eks/k8s/*.yaml
LBC_SA=aws-load-balancer-controller  # must match local.lbc_service_account in eks/terraform/provider.tf
LBC_CHART_VERSION=3.6.2              # same version as eks/terraform/policies/lb-controller-iam-policy.json

# Terraform and Jenkins may both deploy at the same time: take turns
exec 9>>/var/lib/eks-deploy.lock
echo "==> Waiting for the deploy lock"
flock 9

echo "==> Build and push $IMAGE"
aws ecr get-login-password --region "$REGION" | docker login --username AWS --password-stdin "${ECR_REPO%%/*}"
docker build -q -t "$IMAGE" "$APP_DIR"
docker push -q "$IMAGE"
docker image prune -f >/dev/null

echo "==> Connect to private cluster $CLUSTER"
aws eks update-kubeconfig --region "$REGION" --name "$CLUSTER" >/dev/null
# Same kubeconfig for ec2-user, so "kubectl" works right after you SSH in (uses the EC2's IAM role)
if [ "$(id -u)" = 0 ]; then
  sudo -u ec2-user -H aws eks update-kubeconfig --region "$REGION" --name "$CLUSTER" >/dev/null
fi
kubectl get nodes -o wide

echo "==> AWS Load Balancer Controller $LBC_CHART_VERSION"
# Its IAM role comes from Pod Identity (eks/terraform/cluster.tf)
helm repo add eks https://aws.github.io/eks-charts --force-update >/dev/null
helm upgrade --install aws-load-balancer-controller eks/aws-load-balancer-controller \
  --namespace kube-system \
  --version "$LBC_CHART_VERSION" \
  --set clusterName="$CLUSTER" \
  --set region="$REGION" \
  --set vpcId="$VPC_ID" \
  --set serviceAccount.create=true \
  --set serviceAccount.name="$LBC_SA" \
  --set keepTLSSecret=true \
  --wait --timeout 5m
# The webhook certificate lives in a Secret that the pods read only at startup. Restart them so they
# always serve the certificate the webhook configuration trusts (otherwise: "x509: certificate signed by unknown authority")
kubectl rollout restart deployment/aws-load-balancer-controller --namespace kube-system
kubectl rollout status deployment/aws-load-balancer-controller --namespace kube-system --timeout 3m

echo "==> Namespace, service account, config"
kubectl apply -f "$K8S_DIR/00-namespace.yaml" -f "$K8S_DIR/01-serviceaccount.yaml"

# create-or-update (ASP.NET reads "__" as ":" -> S3:BucketName etc.)
kubectl create configmap sample-app-config --namespace "$NAMESPACE" \
  --from-literal=AWS__Region="$REGION" \
  --from-literal=S3__BucketName="$BUCKET" \
  --from-literal=S3__KeyPrefix="$UPLOAD_PREFIX" \
  --dry-run=client -o yaml | kubectl apply -f -

# RDS: the master password lives in Secrets Manager (created by RDS); the pods get the full
# connection string as ConnectionStrings__Rds from a Kubernetes Secret
DB_SECRET=$(aws secretsmanager get-secret-value --region "$REGION" --secret-id "$RDS_SECRET_ARN" \
  --query SecretString --output text)
DB_USER=$(jq -r .username <<<"$DB_SECRET")
DB_PASS=$(jq -r .password <<<"$DB_SECRET")
kubectl create secret generic sample-app-db --namespace "$NAMESPACE" \
  --from-literal=ConnectionStrings__Rds="Host=$RDS_HOST;Port=$RDS_PORT;Database=$RDS_DATABASE;Username=$DB_USER;Password=\"$DB_PASS\";SSL Mode=Require" \
  --dry-run=client -o yaml | kubectl apply -f -

echo "==> Deploy $IMAGE"
sed "s|IMAGE_PLACEHOLDER|$IMAGE|" "$K8S_DIR/02-deployment.yaml" | kubectl apply -f -
kubectl apply -f "$K8S_DIR/03-service.yaml" -f "$K8S_DIR/04-ingress.yaml"

# ConfigMap/Secret changes don't restart pods on their own
kubectl rollout restart deployment/sample-app --namespace "$NAMESPACE" >/dev/null

if ! kubectl rollout status deployment/sample-app --namespace "$NAMESPACE" --timeout 5m; then
  kubectl get pods --namespace "$NAMESPACE" -o wide
  kubectl describe pods --namespace "$NAMESPACE" -l app=sample-app | tail -40
  exit 1
fi
kubectl get pods --namespace "$NAMESPACE" -o wide

echo "==> Waiting for the ALB address"
HOST=""
for _ in $(seq 1 30); do
  HOST=$(kubectl get ingress sample-app --namespace "$NAMESPACE" -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
  [ -n "$HOST" ] && break
  sleep 10
done
if [ -z "$HOST" ]; then
  echo "Ingress has no ALB yet:"
  kubectl describe ingress sample-app --namespace "$NAMESPACE"
  kubectl logs --namespace kube-system deployment/aws-load-balancer-controller --tail 30
  exit 1
fi
kubectl get ingress --namespace "$NAMESPACE"

echo "==> Waiting for http://$HOST (new ALBs need 2-4 minutes for DNS + health checks)"
for _ in $(seq 1 40); do
  if curl -fsS -o /dev/null --max-time 5 "http://$HOST/swagger/index.html"; then
    echo
    echo "App is up:"
    echo "  Swagger UI : http://$HOST/swagger"
    echo "  Upload     : curl -F file=@README.md http://$HOST/api/files/upload"
    exit 0
  fi
  printf '.'
  sleep 15
done
echo
echo "ALB not answering yet - try http://$HOST/swagger again in a few minutes, or check:"
echo "  ./eks/scripts/kubectl.sh describe ingress sample-app -n sample-app"
# Not a failure: the app is deployed, only DNS/health checks are still settling
```

**Key points:**

- Usage: `deploy-app.sh <image_tag>`. Jenkins runs it as `jenkins` from its checkout; `deploy.tf` runs it with `sudo` from the files copied from your laptop. Both have the repo layout, so the script finds `app/` and `eks/k8s/` relative to itself.
- Settings come from `/etc/eks-deploy.env` (written by `jenkins.tf`).
- `flock` on `/var/lib/eks-deploy.lock`: if Terraform and Jenkins deploy at the same time, the second one waits.
- `PATH=/usr/local/bin:$PATH`: kubectl and helm live there, and `sudo` drops it from `PATH`.
- **Build + push:** `aws ecr get-login-password | docker login` uses the deployer's IAM role. `${ECR_REPO%%/*}` keeps only the registry host. `-q` keeps the apply log short.
- `aws eks update-kubeconfig` points kubectl at the **private** endpoint. It works only because the deployer is in the VPC and has an access entry. The same kubeconfig is written for `ec2-user`, so `kubectl` works when you SSH in.
- **LB controller:** `helm upgrade --install` installs it the first time and upgrades it (or does nothing) after that. `clusterName`, `region` and `vpcId` are passed, so the controller does not need EC2 metadata. Its IAM role comes from Pod Identity. `--wait` blocks until it is ready.
- `keepTLSSecret=true` + `rollout restart`: the controller's admission webhook uses a self-signed certificate stored in a Secret, and the pods read it only at startup. Without these, a second `helm upgrade` creates a new certificate while old pods keep serving the old one. Applying the Service/Ingress then fails with *x509: certificate signed by unknown authority*.
- **ConfigMap:** `kubectl create configmap ... --dry-run=client -o yaml | kubectl apply -f -` means create-or-update.
- **RDS Secret:** reads the username and password from Secrets Manager and stores the whole connection string in the Secret `sample-app-db`. The Deployment loads it with `envFrom`, so the app sees `ConnectionStrings__Rds`.
- **Deploy:** `sed` swaps `IMAGE_PLACEHOLDER` for the real image. `rollout restart` makes ConfigMap/Secret changes take effect. `rollout status` waits up to 5 minutes and prints pod details on failure.
- **ALB address:** waits for the Ingress hostname, then curls the ALB until it answers (a new ALB needs 2-4 minutes for DNS and health checks) and prints the Swagger URL.

The job **eks-sample-app** is already there. **Run it once by hand** (*Build Now*): a pipeline job only learns

**Connect GitHub (instant builds):** in the GitHub repo -> *Settings* -> *Webhooks* -> *Add webhook*:

| Field | Value |
| --- | --- |
| Payload URL | `terraform output -raw github_webhook_url` (`http://<elastic-ip>:8080/github-webhook/`) |

| Events | *Just the push event* |

Adding a webhook needs admin rights on the repo. Without it, Jenkins still picks up a push within ~2 minutes (polling).

## 10. Troubleshooting

| Symptom | Likely cause | Check or fix |
| --- | --- | --- |
| `timeout - last error: dial tcp <ip>:22` during apply | Your public IP changed, or a firewall blocks port 22 | `curl https://checkip.amazonaws.com`, then `terraform apply` again (updates the SSH rule), or set `admin_cidrs` |
| Jenkins page doesn't open | Your IP changed, or Jenkins is still starting | `terraform apply` (updates the rule); `./eks/scripts/ssh.sh sudo systemctl status jenkins` |
| Push doesn't start a build | No webhook, or wrong branch | Wait 2 minutes (polling). GitHub -> Settings -> Webhooks -> *Recent Deliveries* should show 200. Check `github_branch` |
| Jenkins build: `eks/Jenkinsfile` not found | `eks/` isn't pushed to the branch | Commit and push the `eks/` folder |
| Jenkins build: `permission denied ... docker.sock` | Jenkins started before it joined the docker group | `./eks/scripts/ssh.sh sudo systemctl restart jenkins` |
| `/api/database/connection` returns 503 | Pods can't reach RDS, or the Secret is missing | `./eks/scripts/kubectl.sh get secret sample-app-db -n sample-app`; check the `rds_from_pods` rule in `rds.tf` |
| `terraform destroy`: *DependencyViolation ... has some mapped public address(es)* on the internet gateway/subnets | The ALB created by Kubernetes is still there (the Ingress couldn't be deleted) | Delete the `sampleapp-eks` load balancer, its `k8s-...` target group and `k8s-...` security groups in the EC2 console, then `terraform destroy` again |
| `ssh: Permission denied (publickey)` | Wrong key or user | Use `ec2-user` and `eks/terraform/deployer-key.pem` (`./eks/scripts/ssh.sh` does both) |
| Apply stops after "Waiting for user data" | kubectl/helm download failed | The log tail is printed; or `./eks/scripts/ssh.sh sudo cat /var/log/user-data.log` |
| `terraform plan` hangs on `STS: GetCallerIdentity` | The network stalls TLS handshakes without ML-KEM | `export GODEBUG=tlsmlkem=1` (section 2) |
| Build fails | Dockerfile/app error, or out of disk | The error is in the Jenkins console (or the `terraform apply` log); fix it and push again |
| kubectl from your laptop times out | Expected: the API is private | Use `./eks/scripts/kubectl.sh` |
| Node group stuck in *Creating*, 0 nodes | Instance type not allowed (Free plan) | EC2 -> Auto Scaling groups -> `eks-...-ng-default` -> *Activity*. Use a Free Tier type such as c7i-flex.large |
| Nodes not `Ready` | Add-ons still installing, or no NAT route | `./eks/scripts/kubectl.sh get pods -n kube-system` |
| Pods in `ImagePullBackOff` | Image not pushed | `./eks/scripts/kubectl.sh describe pod -n sample-app -l app=sample-app` |
| Pods in `CrashLoopBackOff` | App error | `./eks/scripts/kubectl.sh logs -n sample-app deployment/sample-app` |
| `failed calling webhook "mservice.elbv2.k8s.aws"` ... `x509: certificate signed by unknown authority` | LB controller pods serve an old webhook certificate | `terraform apply -replace=terraform_data.deploy` (it restarts the controller), or `./eks/scripts/kubectl.sh rollout restart deployment/aws-load-balancer-controller -n kube-system` |
| AWS output stops at `(END)` | AWS CLI pager | Press `q`, or `export AWS_PAGER=""` |
| Ingress has no address | LB controller not running, or subnet tags missing | `./eks/scripts/kubectl.sh logs -n kube-system deployment/aws-load-balancer-controller --tail 50` |
| ALB returns 502/503 | Targets still registering | Wait 2-3 minutes; check target group health in the EC2 console |
| Upload returns 502 | Pod has no S3 permission | Check the Pod Identity association `sample-app/sample-app` in the EKS console -> Access tab |

## 11. Cleanup

EKS is billed by the hour, so destroy it when you're done:

```bash
cd ~/5monthsdevopstraining/eks/terraform
terraform destroy             # stops Jenkins, deletes the Ingress/ALB over SSH, then everything else (type "yes")
```

**Rough cost while running:** EKS control plane about $0.10/hour, 3 x c7i-flex.large (2 nodes + the
deployer/Jenkins), RDS db.t4g.micro, the NAT gateway, the Elastic IP and the ALB. That is about **$0.45-0.50/hour** in total.

`terraform destroy` also deletes the RDS database (no final snapshot) and the uploaded files in S3.
